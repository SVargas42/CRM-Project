For an anchored production read, verification runs at these exact boundaries:

1. Database.Open calls SqlCipherConnectionFactory.Open, which verifies runtime, keys/checks the connection, acquires checkpoint ownership and calls SecurityAudit.Verify then Commit in a preliminary transaction when an anchor exists.
2. Service ReadOperation starts its own transaction. AccessControl.IdentityCore calls SecurityAudit.Verify before session/user lookup.
3. Verify calls VerifyFreshness and VerifyPrefix. On first use per transaction, VerifyFreshness calls ReadHead, which itself runs VerifyPrefix before the trusted checkpoint comparison. A ConditionalWeakTable caches the transaction's freshness/checkpoint value; it does not cache every chain verification.
4. After the SELECT and session recheck, ReadOperation calls Append(Sessions,0,AccessVerified). Append again invokes VerifyPrefix before signing/inserting.
5. Commit calls ReadHead for the resulting head, invoking VerifyPrefix again, then coordinates checkpoint state and SQLite commit through TrustedAuditProtocol.Commit.

**Cost / D08:** VerifyPrefix recomputes LegacyDigest over all historical boundary rows, then scans all later rows ordered by ID, checks continuity and recomputes chained HMACs. One full scan is O(N) row visits plus payload bytes. There are repeated full scans per connection/read/append/commit, and successful reads append new entries. A fixed number of scans as history grows through N entries gives **O(N²) cumulative work**. R reads starting with N entries give O(RN+R²) row visits when each appends a constant number of events. These are static loop-derived bounds, not a claim that one verification internally has nested quadratic loops. Production timings/scale thresholds: **NOT FOUND** in this discovery.
